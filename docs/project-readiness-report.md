# تقرير جاهزية مشروع Dropify للاستخدام الواقعي

تاريخ المراجعة: 17 سبتمبر 2026  
آخر تحديث تنفيذي: 23 سبتمبر 2026

## الخلاصة

المشروع أصبح **مرشحًا جيدًا لبيئة staging واختبارات بوابات الدفع**، لكنه **ليس جاهزًا بعد لاستقبال مدفوعات إنتاج حقيقية**. موانع الإطلاق الحالية تشغيلية وخارجية في معظمها: ترحيلات جديدة لم تطبق على قاعدة الإنتاج، مفاتيح البوابات والبريد الحقيقية غير موجودة في البيئة الحالية، ولم تنفذ اختبارات sandbox وE2E أو خطة تخزين صور ومراقبة ونسخ احتياطي.

> تنبيه امتثال: Paddle وLemon Squeezy يحظران السلع المادية حاليًا. التكاملان المضافان صالحان لاختبارات sandbox أو لكتالوج رقمي معتمد فقط، ولا يجوز تفعيلهما لطلبات الدروبشيبنغ المادية الحالية.

## ما تم تصحيحه داخل المشروع

### مراجعة 23 سبتمبر 2026

- أصبح دمج سلة الضيف بعد تسجيل الدخول مشروطًا بخلو سلة الضيف وسلة العميل من محاولة دفع نشطة، مع قفل صفّي السلتين أثناء النقل وإعادة المحاولة عند أول تعديل لاحق للسلة. هذا يمنع إضافة عناصر إلى سلة مقفلة ثم حذفها عند تأكيد الدفع.
- يتحقق ويبهوك Stripe من مرجع جلسة Checkout المرتبط بالطلب، ويتحقق عند تأكيد الاسترداد من طلب الاسترداد المسجل والمبلغ والعملة ومرجع PaymentIntent.
- أصبح إكمال الاسترداد انتقالًا شرطيًا واحدًا يستخدمه كل من الويبهوك ولوحة الإدارة؛ فلا يعاد تسجيل الحدث الإداري عند السباق بينهما، ولا تعيد استجابة بوابة متأخرة حالة الاسترداد الناجح إلى `PENDING` أو `FAILED`.
- بقيت اختبارات تكامل قاعدة البيانات والبوابات مطلوبة. قاعدة البيانات المتصلة بهذه البيئة لا تزال تعرض ثلاث ترحيلات غير مطبقة، لذلك لم تُشغَّل عليها عمليات كتابة أو اختبارات دفع.

### دورة الدفع والطلب المهجور

- أضيفت مهلة فعلية لكل checkout مع تخزين `providerCheckoutId` و`paymentExpiresAt` في [`prisma/schema.prisma`](../prisma/schema.prisma).
- أضيفت تسوية مع Stripe وPayPal وMoyasar وPaddle وLemon Squeezy وإلغاء المحاولات المنتهية وتحرير قفل السلة والمخزون في [`lib/payments/lifecycle.ts`](../lib/payments/lifecycle.ts).
- أضيف endpoint مجدول محمي بـ`CRON_SECRET` في [`app/api/cron/reconcile-payments/route.ts`](../app/api/cron/reconcile-payments/route.ts). يجب ربطه بجدولة خارجية كل خمس دقائق على الأقل.
- أضيف سجل دائم لأحداث الويبهوك مع منع التكرار وحالات المحاولة والفشل في [`lib/payments/events.ts`](../lib/payments/events.ts).
- أصبحت أحداث Stripe وPayPal وMoyasar وPaddle وLemon Squeezy الفاشلة تعاد بحالة قابلة لإعادة المحاولة بدل بقائها عالقة في `PROCESSING`.
- عند فشل إنشاء الدفع بصورة مؤكدة، يلغى الطلب وتحرر السلة والمخزون. أما النتيجة غير المؤكدة فتبقى محفوظة للتحقيق حتى لا ينشأ خصم مزدوج.

### الاسترداد المالي

- زر `REFUNDED` لم يعد يغيّر قاعدة البيانات فقط؛ أصبح يستدعي Refund API الحقيقي للبوابة في [`lib/payments/provider-operations.ts`](../lib/payments/provider-operations.ts).
- Stripe يستخدم PaymentIntent ومفتاح idempotency، وPayPal يستخدم capture ID و`PayPal-Request-Id`، وMoyasar يستخدم payment ID، وPaddle يستخدم adjustment، وLemon Squeezy يستخدم order refund.
- أضيف سجل `Refund` بالمبلغ والعملة والسبب والمرجع والحالة، ولا تتحول حالة الطلب إلى `REFUNDED` إلا بعد تأكيد البوابة.
- الاستردادات المعلّقة في البوابات الخمس تدخل في مهمة reconciliation الدورية. النتائج غير المؤكدة من البوابات التي لا توفر مفتاح idempotency تنتقل إلى `NEEDS_REVIEW` بدل إعادة عملية قد تسترد المبلغ مرتين.
- منعت لوحة الإدارة التحويل اليدوي الخطر من `PENDING` إلى `PAID` أو من طلب مدفوع إلى `CANCELLED`؛ الإلغاء والاسترداد يمران عبر المسار الصحيح.

### المخزون ومنع البيع الزائد

- أضيف SKU و`stockQuantity` و`reservedQuantity` وتتبع اختياري للمخزون على المنتج وكل variant.
- يحجز المخزون داخل transaction عند إنشاء الطلب، ويخصم بعد تأكيد الدفع، ويحرر عند الإلغاء أو انتهاء checkout في [`lib/inventory.ts`](../lib/inventory.ts).
- تستخدم عملية الحجز تحديثًا شرطيًا متفائلًا لمنع تجاوز المخزون عند محاولات checkout المتزامنة.
- تتحقق السلة وصفحة الدفع من الكمية المتاحة بعد طرح الحجوزات، وليس من علم `inStock` فقط.
- أضيفت حقول إدارة SKU والكمية والحجز، مع منع خفض الكمية تحت الحجوزات أو حذف variant محجوز.

### الأمان والتشغيل

- أضيفت CSP وHSTS و`X-Frame-Options` و`nosniff` وReferrer/Permissions Policy في [`next.config.ts`](../next.config.ts).
- خفض حد Server Actions من 25MB إلى 21MB، وهو الحد اللازم لمسار رفع صور الإدارة الحالي.
- أضيف rate limiting مشترك عبر PostgreSQL للـcheckout والسلة والتحليلات، مع تخزين بصمة مشفرة لعنوان العميل بدل العنوان الخام في [`lib/rate-limit.ts`](../lib/rate-limit.ts).
- Rate limiting للمصادقة مخزن أيضًا في PostgreSQL عبر Better Auth.
- أضيف `AdminAuditLog` لتغييرات حالة الطلبات والإلغاء والاسترداد.
- أضيف فحص شامل لإعدادات الإنتاج عند startup في [`lib/environment.ts`](../lib/environment.ts)، وفصل build عن migration عبر `npm run release`.
- أضيف health endpoint في [`app/api/health/route.ts`](../app/api/health/route.ts) وCI يشغل التوليد وlint وtypecheck والاختبارات والبناء في [`.github/workflows/ci.yml`](../.github/workflows/ci.yml).
- رُفعت النسخ الفرعية الآمنة من `fast-uri` و`mysql2`. انخفض `npm audit --omit=dev` من 5 إلى 3 إدخالات عالية، والمتبقي كله سلسلة واحدة من `deepmerge-ts` عبر أداة Prisma.

### SEO والأداء

- أضيف [`app/robots.ts`](../app/robots.ts) و[`app/sitemap.ts`](../app/sitemap.ts) مع روابط اللغتين وصور المنتجات.
- أضيفت metadata ديناميكية وcanonical وhreflang وOpen Graph وProduct JSON-LD لكل منتج.
- أصبحت pagination في واجهة المنتجات تستخدم `count` و`skip/take` داخل PostgreSQL بدل تحميل جميع المنتجات ثم قص المصفوفة في الذاكرة.
- صححت صفحة نجاح الطلب صياغتها؛ لم تعد تجزم بوصول البريد عندما قد يفشل مزود البريد.

## نتائج التحقق الحالية

- `npm test`: نجح **30/30**.
- `npm run lint`: نجح.
- `npm run typecheck`: نجح.
- `npx prisma validate`: نجح.
- `npm run build`: نجح بالكامل، بما في ذلك مسارات health وcron وrobots وsitemap.
- `git diff --check` على الملفات المصدرية: لا توجد أخطاء whitespace.
- `npx prisma migrate status`: نجح الاتصال بقاعدة البيانات، لكن الترحيلات التالية تحتاج إلى التطبيق على بيئة النشر:
  - `20260920120000_payment_lifecycle`
  - `20260920130000_inventory_reservations`
  - `20260920140000_add_paddle_lemonsqueezy`
- `npm audit --omit=dev`: بقيت 3 إدخالات عالية مترابطة (`prisma` ← `@prisma/config` ← `deepmerge-ts`). الإصلاح المقترح من npm هو downgrade/تغيير رئيسي غير آمن، لذلك لم يطبق تلقائيًا.

الاختبارات الجديدة تغطي التحقق من بيئة الإنتاج، مسارات صور الحساب، تحويل العملات، حساب المخزون المتاح بعد الحجوزات، والتحويل الدقيق لمبالغ مزودي الدفع. ما زالت اختبارات التكامل وE2E مطلوبة كما هو موضح أدناه.

## موانع الإطلاق التجاري المتبقية

### 1. الترحيلات وأسرار الإنتاج واختبارات البوابات

لا يجوز توجيه traffic حقيقي قبل:

1. أخذ نسخة احتياطية ثم تشغيل `npm run release` مرة واحدة على قاعدة الإنتاج.
2. التأكد من أن `prisma migrate status` يعرض جميع الترحيلات مطبقة.
3. إدخال نطاق HTTPS وأسرار Auth وResend ومفاتيح Stripe وMoyasar وPayPal وwebhook IDs الحقيقية خارج المستودع.
4. تنفيذ دورة دفع كاملة في sandbox لكل بوابة: نجاح، إلغاء، انتهاء مهلة، webhook مكرر، webhook متأخر، refund ناجح وrefund معلق.
5. جدولة endpoint التسوية ومراقبة نتائج فشله.

هذه الخطوات لم تنفذ تلقائيًا لأنها تغيّر قاعدة وخدمات خارجية فعلية وتتطلب مفاتيح وقرار نشر من المالك.

### 2. الاختبارات غير كافية للإطلاق المالي

لا تزال مطلوبة:

- اختبارات integration حقيقية لـcheckout والتزامن وحجز المخزون.
- fixtures موقعة لويبهوكات البوابات الخمس وحالات replay/failure.
- اختبارات صلاحيات الإدارة والسلة ودمج سلة الضيف.
- اختبارات sandbox للاسترداد والتسوية.
- اختبار إرسال البريد وفشله وإعادة المحاولة.
- تدفق شراء E2E من إضافة المنتج حتى ظهور الطلب في حساب العميل ولوحة الإدارة.

### 3. تخزين الصور

الصور ما زالت تكتب داخل `public/uploads` في [`actions/account.ts`](../actions/account.ts) و[`actions/admin.ts`](../actions/admin.ts). هذا يصلح لخادم واحد بقرص دائم، ولا يصلح لـVercel أو عدة instances. يجب اختيار S3 أو R2 أو Cloudinary، مع سياسة حذف ونسخ احتياطي، قبل النشر على بنية ephemeral.

### 4. المراقبة والاستعادة

أصبح هناك health endpoint وCI وبيانات webhook/refund قابلة للتحقيق، لكن ما زال ينقص:

- Sentry أو بديل لتجميع الأخطاء والتنبيه.
- تنبيه على فشل cron والويبهوكات والبريد وحالات `NEEDS_REVIEW`.
- سجلات منظمة مع correlation IDs.
- نسخ احتياطي لقاعدة البيانات واختبار استعادة موثق.
- بيئة staging منفصلة وخطة rollback للترحيلات والتطبيق.
- سجل بريد دائم ومحاولات retry؛ البريد حاليًا يسجل الفشل في الخادم فقط.

### 5. الجوانب التجارية والقانونية

لا يمكن كتابة سياسات قانونية صحيحة من دون دولة المنشأة وبياناتها ونطاق البيع والضريبة وسياسة المورد. يلزم اعتماد ونشر:

- الخصوصية والشروط وسياسة ملفات الارتباط وموافقة التحليلات.
- الشحن والإرجاع والاسترداد بأزمنة وعناوين فعلية.
- VAT/الضرائب والفواتير وبيانات المنشأة حسب دولة التشغيل.
- آلية طلب حذف/تصدير بيانات العميل.

### 6. سلسلة Prisma الأمنية

المتبقي في audit هو stack exhaustion في `deepmerge-ts` المستخدم داخل `@prisma/config`. لا يوجد تحديث Prisma مستقر في السلسلة الحالية يزيله، وفرض `deepmerge-ts` 8 قد يكسر Prisma. يجب متابعة تحديث Prisma الرسمي، وتشغيل أدوات Prisma في CI/release فقط مع ملفات إعداد موثوقة وعدم تعريضها لمدخلات المستخدم.

### 7. وظائف dropshipping والتوريد

ما يزال إدخال AliExpress والمراجعات يدويًا. لا توجد مزامنة سعر/مخزون المورد، أو إنشاء طلب المورد، أو شركة شحن ورقم تتبع وسجل fulfillment. هذه ليست أخطاء دفع مباشرة، لكنها ضرورية إذا كان الهدف تشغيل dropshipping آليًا.

## ترتيب الإطلاق المقترح

1. اختيار object storage وبيئة staging وربط المراقبة والنسخ الاحتياطي.
2. إدخال أسرار sandbox وتشغيل الترحيلات الجديدة على staging.
3. تشغيل اختبارات integration وE2E وحالات الويبهوك والاسترداد المذكورة أعلاه.
4. إكمال واعتماد السياسات والضرائب والشحن والتتبع.
5. تشغيل `npm run release` على الإنتاج والتحقق من migration status وhealth.
6. إجراء طلب صغير حقيقي ثم Refund فعلي لكل بوابة ومطابقة سجلات البوابة مع `PaymentEvent` و`Refund`.
7. فتح traffic تدريجيًا مع تنبيهات ومراجعة يومية للحالات المعلقة في الأسبوع الأول.

## الحكم النهائي

الإصلاحات البرمجية الأعلى خطورة في التقرير السابق—السلة المقفلة، الاسترداد الشكلي، غياب المخزون، غياب dedup للويبهوكات، الترويسات الأمنية، rate limiting، health/CI، وSEO الأساسي—أُنجزت. المنع الحالي ليس ادعاءً عامًا بأن الكود غير صالح، بل شرط إطلاق واضح: **لا مدفوعات حقيقية قبل تطبيق الترحيلات الجديدة، واختبار البوابات فعليًا، ونقل الصور، وتجهيز المراقبة والنسخ الاحتياطي والسياسات**.
